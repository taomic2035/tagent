# 第 5 章 记性：上下文管理与遗忘的艺术

> 本章目标：解决"聊久了会变傻变贵"——写 token 估算器（零依赖）、双水位裁剪
> （回合完整 + KV cache 前缀稳定）、做一次影响全书的**设计决策课**（用户消息
> 一个字都不能动）、搭摘要压缩阶梯（含一次真实的"越压越大"翻车）、
> 最后给 agent 一个跨会话的长期记忆。预计 1 天。

---

## 5.1 问题：上下文是有限且计费的记性

第 2 章实验 3 埋的线：每轮对话都是**全量历史重发**。两个后果：

1. **上下文窗口有上限**（Qwen3.5 约 32K token）：聊到上限，请求直接报错
2. **每轮都在为历史付费**：prompt token 每轮重算（除非命中 KV cache），
   CPU 上还意味着每轮等更久

上下文管理 = 决定"模型此刻能看见什么"。手段从轻到重：**裁剪**（丢弃）、
**降级**（压缩成一行）、**摘要**（LLM 改写）。全部都要在本章学会。

## 5.2 token 估算器：零依赖的够用方案

精确计数需要 tokenizer（分词器）——它依赖具体模型的词表文件，会击穿零依赖红线。
估算器的够用方案（Qwen 系实测校准过的启发式）：

```ts
// packages/core/src/memory.ts
const CJK = /[\u4e00-\u9fff\u3000-\u303f\uff00-\uffef]/g;  // 汉字+中文标点+全角

export function estimateTokens(text: string): number {
  if (!text) return 0;
  const cjk = (text.match(CJK) ?? []).length;
  const other = text.length - cjk;
  return Math.ceil(cjk + other * 0.25);     // 中文≈1字1token，英文≈4字符1token
}

// 消息级估算：每条消息加固定协议开销（role 标记/结构字符，实测约 4）
export function estimateMessagesTokens(messages: ChatMessage[]): number {
  return messages.reduce((sum, m) => {
    let t = 4;
    if (m.role === "tool") t += estimateTokens(m.content);
    else if (m.role === "assistant") {
      t += estimateTokens(m.content ?? "");
      for (const tc of m.tool_calls ?? [])
        t += estimateTokens(tc.function.name) + estimateTokens(tc.function.arguments) + 4;
    } else t += estimateTokens(m.content);
    return sum + t;
  }, 0);
}
```

估算必须**单调**（子串 ≤ 全文）且**稳定**（同输入同输出）——这两个性质是后面
所有裁剪决策可复现的前提。给两个测试锚点：`estimateTokens("北京今天天气") === 6`、
`estimateTokens("abcdefgh") === 2`。

> **诚实边界**：估算与真实 token 误差约 ±10%。对"预算控制"够用（预算本来就是
> 软限制）；需要精确账目的实验，用引擎返回的 usage 字段（第 1 章讲过）。

## 5.3 双水位裁剪：遗忘也要讲工程

裁剪的直觉做法是"超了就删最旧的一条"——**错得很有教学价值**：

1. 删一条导致某条 `tool` 消息找不到配对的 `tool_calls`（第 3 章配对纪律被自己
   破坏）→ 引擎直接 400
2. 每轮删一点 = **每轮请求前缀都变** → KV cache 永远全量失效（下一节实测代价）

正确姿势是**双水位（high/low water mark）**：

```ts
export interface TrimPolicy { budget: number; lowRatio?: number }   // 缺省 0.5

export function trimMessages(messages: ChatMessage[], policy: TrimPolicy) {
  const low = Math.ceil(policy.budget * (policy.lowRatio ?? 0.5));
  // 以"用户轮"为单位，从最旧开始整块丢弃轮内工作，一次裁到低水位以下
  // "最近 1 个工作单元"保留（正在用的数据不能抽走）；user/system 恒保
  // ——完整实现见章末清单与参考实现 memory.ts（含溢出标志）
}
```

三条铁律（每条都有翻车实录背书）：

- **回合完整**：裁剪单位是完整轮次（user + 其 assistant/tool 配对），绝不裁半轮
- **一次到位**：触发即裁到低水位（预算 50%），下次触发前请求前缀完全不变
- **正在用的不能抽**：最近的工作单元保留——第 3 章场景 4 里模型刚查的上海天气
  被裁掉，它会当场再查一遍（行为退化成复读）

## 5.4 KV cache：为什么裁剪方式决定速度

KV cache（0.3 术语表）的原理：引擎对已见过的 prompt 前缀缓存计算结果，
**前缀逐字节不变**则直接复用。看真机对比（llama.cpp 日志的 `cache_n` 字段）：

| 裁剪策略 | 请求间前缀 | KV 命中（实测） | 千 token 处理耗时 |
|---|---|---|---|
| 双水位（两次触发间不变） | 稳定 | **78%** | 约 1/5 |
| 每轮裁一点 | 每轮都变 | ≈0% | 全价 |

这就是"一次裁到低水位"的全部理由：**遗忘的颗粒度，直接换算成速度**。
llama.cpp 的 `/metrics` 端点与日志 `timings.cache_n` 都能直接观察命中率——
做本章实验时盯着它，你会对"前缀稳定"四个字有手感。

## 5.5 设计决策课：用户消息一个字都不能动

裁剪难免碰到 user 消息。一个真实发生过的设计讨论，完整重演给你（这是全书
最重要的一节决策训练）：

**问题一：重复的用户消息可以去重吗？**
> 可以，但**仅限字节级完全相同的相邻消息**（手滑重发）。
> "意思一样就合并"是语义判断 = 改写，不做。

**问题二：语气词、错别字可以清理吗？"反正意思不变，还能省 token"？**
> 不行，三个结构性理由：
> 1. **破坏复现**：存证里发的请求是清理版，用户手敲的是原文——"同一任务手敲
>    能复现"的制度直接断裂（第 9 章会把它立成验收标准）
> 2. **风险不对称**：错别字可能承载意图（方言/缩写/黑话被"修正"= 篡改指令）；
>    语气词本身是指令强度信息（"麻烦你了"≠"赶紧！"）。清理省几十 token，
>    改错赔整个任务
> 3. **改写者不可靠**：让 4B 判断什么是错别字，改错的概率比错别字本身的危害大

**问题三：那"永不压缩"到底多强？极端超预算怎么办？**
> 分层：改写——永不；降级（工具结果压成一行，消息还在）——可以；
> 丢弃——轮内工作可以，user 消息**宁可报错拒续也不丢**。
> 参考实现为此修了三版 trim（死循环→保护过度→单元级丢弃），教训入档：
> **每版都是被测试逼出来的**。教程带你直接落最终版，但请记住这个决策链条的形状：
> 先定原则（什么绝不动），再谈手段（丢/压/摘的次序），最后留出口（报错也是诚实）。

## 5.6 摘要压缩：阶梯式，且要算账

裁剪是丢弃（信息没了），摘要是有损保留。设计成阶梯，能用便宜手段就不上贵的：

```
阶段 0：相邻去重（字节级，零成本）
阶段 1：确定性降级——旧工具结果压成一行（零 LLM 成本）：
        "[工具结果已降级｜原文约N字] 前120字…"
阶段 2：LLM 摘要——实在超了，把被压轮的工作交给一次模型调用改写成一段；
        被压轮的 user 原文钉住不动，摘要以 user 角色注入（"（系统注入：历史工作摘要…）"）
兜底：  摘要后仍超 → 回到裁剪（丢弃 ≠ 改写，事件上严格区分）
```

**真机翻车实录：摘要越压越大（327 → 362）**。钉住的 user 原文占大头、被压的
工作很小时，摘要产物（原文 + 摘要 + 标注）比原文还长——白花一次 LLM 调用。
修法是**划算预检**：摘要长度上限可估（提示词限 150 字 + anchor），产物预估
不小于原文就跳过摘要直接走裁剪。教训泛化：**压缩是增益不是义务，先算账再动手**。

另一个跨引擎坑：摘要消息一开始用 system 角色、放在消息中间——llama.cpp 的
Qwen 模板直接 500（`System message must be at the beginning`）。**上下文注入一律
user 角色 + （系统注入：…）标注**，与第 4 章降级注入同一惯例。

## 5.7 长期记忆：一个 JSONL 文件，够了

上下文管理管的是"这轮对话"，长期记忆管"跨会话"。三件套：

```ts
// 追加式 JSONL 存储（写零成本；量级到万条再谈索引——YAGNI）
export class MemoryStore {
  private facts: MemoryFact[] = [];      // {id, ts, content, tag?}
  constructor(private file: string) { /* 存在则逐行加载 */ }
  append(content: string, tag?: string): MemoryFact { /* 追加文件+内存 */ }
  recall(query: string, k = 5): RecalledFact[] {
    // 手写评分：字符 bigram 交集 + 分词交集×2（中文无空格，bigram 友好）
    // 0 分不返回——宁缺勿滥，无关的记忆注入比没有更糟（污染上下文+占预算）
  }
}
```

再把 remember / recall 包成两个工具（第 3 章的 Tool 接口），模型就能在对话里
自主决定"这值得记"。关键验收结论（真机 A/B）：**召回做成工具让模型按需调用，
优于启动时静态注入**——静态注入每轮占预算，工具召回按需付费。
（第三种"每问一句都自动召 回注入"是反模式：无关问题也吃进上下文。）

## 5.8 动手做与搞坏实验

- **实验 1（估算器校准）**：抓 5 份第 1 章式存证，比对 `estimateMessagesTokens`
  与引擎 usage.prompt_tokens——记录你的误差表（参考实现 ±10% 内）
- **实验 2（KV 命中观察）**：多轮对话中看 llama.cpp 日志 `cache_n` 逐轮变化；
  然后故意把裁剪改成"每轮删一条"，看命中率归零、每轮变慢——亲手复现 5.4 的表
- **实验 3（裁剪回归）**：开 `--max-context-tokens 600` 聊七轮天气（每轮换城市），
  验收：无 400 报错、配对完整（/dump 检查）、最终总结轮仍能说出前面城市的温度
  （信息经压缩存活）、最后一轮"北京多少度"它会**重查而不是失忆乱编**
- **实验 4（user 钉住）**：把预算压到装不下 user 总量（如 200），期望看到
  **明确的报错拒续**（"预算装不下用户指令总量"）而不是静默丢话
