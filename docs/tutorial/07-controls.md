# 第 7 章 缰绳：v0.9 思考开关与守卫 → v0.10 打断与取消

> 给 agent 装三根缰绳。原理线三节"深入一层"：**思考开关在模板层做什么**、
> **思考与 token 预算的联动**（一个反直觉 A/B）、**为什么半截内容绝不回填**。
> 全章数据来自真机采样。预计 1 天。

---

## 7.1 思考模式：字段、渲染、开关

思考模型在答案前先生成一段推理文本。协议上是独立字段（第 1 章的
`--reasoning-format deepseek` 让它进 `reasoning_content`；有的引擎叫
`reasoning`——客户端双认）。三个工程决定：

1. **渲染分流**：思考灰色斜体、正文正常——用户看得见草稿
2. **思考永不入 messages**：只进事件流渲染。两个原因：回传思考纯浪费 token；
   部分引擎的模板会拒收 assistant 消息里的 reasoning 字段
3. **开关必须在请求级**——为什么，值得单独一节

## 深入一层 ①：enable_thinking 在模板层做什么

第 3 章①建立了世界观：模板把 messages 渲染成文本。思考开关也在这一层生效。
Qwen 系模板里大致是这样的条件（示意）：

```
{% if enable_thinking %}（渲染出思考引导段：先在 <think>…</think> 里推理再作答）
{% else %}（渲染出反指令：跳过思考直接作答）{% endif %}
```

即：**开关改的是渲染产物里的一段指令文本**，不是模型的某个"思考开关参数"——
模型没有这种参数。对比之下，模型文档流传的"在消息里加 /no_think 就能关"——
实测两个引擎都不认：那只是一句模型没学过的咒语。由此强化第 4 章总纲：
**能力开关落在协议字段或引擎参数上；建立在消息文本上的约定是空中楼阁。**

```json
// 请求体扩展字段（llama.cpp 实测有效；缺省不携带——请求体与旧版逐字节同形）
{ "chat_template_kwargs": { "enable_thinking": false } }
```

## 深入一层 ②：思考是预算消费者——一个反直觉 A/B

第 3 章③讲过：`max_tokens` 是**思考+正文+参数共享的池**，`length` 是硬预算闸。
把这条与①组合，推出实验假设：**有限预算下开思考可能更差**。真机 A/B
（11 题 × 3 采样 × 开/关，同引擎同温度；单题对照用 strawberry 数 r）：

| 组 | 成功率 | 单题对照（strawberry） |
|---|---|---|
| 思考 OFF | **94%** | **131 token / 7.9 秒 / 答对**（逐字母数出 3 个 r） |
| 思考 ON | 82% | **1251 token / 90 秒**——其中 1224 是思考，答案还没写完就被闸断 |

换 9B 复测：ON 组 68%——**更差**（更大模型思考更啰嗦，预算吃亏更多）。

两条泛化结论（不是"思考无用论"——大预算/强模型/复杂数学下思考有收益）：
1. **思考是预算消费者**：开思考必须同时给足 max_tokens
2. **默认关、按需开**——第 9 章移动端默认配置的依据

方法论：这是"先实验再配置"的样板。你的任务集上应该复跑（第 10 章结业题）。

## 7.2 v0.9 循环守卫：三种静默失败

第 4 章总表欠的三行。共同特征：**不抛错、也不干活**——错误处理管不住，
要循环里设专门检查点：

| 失败 | 检测 | 对策 | 上限 |
|---|---|---|---|
| 发呆 | 空内容且无调用 | 注入 nudge："请基于已有信息继续" | 连续 3 次放弃，按空终答收场 |
| 复读 | 批次签名（name+键排序参数）连续相同 | 第 3 批附警告；第 5 批不执行、回填说明、走降级 | 5 批硬上限 |
| 截断 | finish_reason==="length" 且有残缺调用 | **不执行**，逐个回填"参数不完整未执行，请重新发起" | — |

签名比较用**键排序的稳定序列化**（`{"b":1,"a":2}` 与 `{"a":2,"b":1}` 同签名）
——同工具不同参数是正常行为（翻页），整批相同才算复读，误报优先级低于漏报。

三条设计原则（守卫自身的兜底，比守卫本身重要）：**可观测**（每个动作发
guard 事件进 transcript——静默的守卫等于没有）；**有限次**（nudge 无限重试
= 把发呆换成死循环）；**注入以 user 入档**（非头部 system 会 500 的坑，
第三次出现）。

**真实采样频率**（守卫价值的诚实标定）：日常任务 10 个——空响应 0 次、
复读 0 次；复读诱发任务 6 个——**复读 1 次**（被第 5 批截停）；小 max_tokens
探针 8 发——截断 0 次（短调用在极小窗口也完整，截断的真实风险集中在
思考开启+紧预算，恰好接上 7.1②）。结论：三守卫频率差异巨大，但成本低、
各自防住明确形态——**保留，文档如实记录频率，不夸大威胁**。

> **引经据典**｜hermes-agent `agent/empty_response_guard.py` / `repetition_guard.py`
> 工业同款三件套（空响应守卫/重复检测/丢调用 nudge），外加预算耗尽后的
> grace call（多给一次收尾）。它连"中途改向"（用户打断）都显式保持
> role 交替与缓存前缀——守卫的每个动作都以不动前缀为约束。

## 7.3 v0.10 steering：agent 干活时你插话

第 3 章循环的体验缺陷：一轮任务内用户毫无插嘴机会。修法（软打断）：

**语义**：不杀正在进行的流/工具，你的话排队，**下一次 LLM 请求前**以 user
消息注入。core 加第 4 参：

```ts
export interface SteeringChannel { take(): string[] }   // 取走即清

// 循环内、round > 1 且请求前（第 1 轮不注入——首轮时用户最新意图就是初始消息）：
if (round > 1 && steering) {
  for (const directive of steering.take()) {
    messages.push({ role: "user", content: directive });
    yield { type: "steering", message: directive };
  }
}
```

两个讲究（每个都回扣前文）：**注入点在裁剪之后**（新指令绝不能被本轮裁掉，
第 6 章的 ordering）；**追加而非改写**（前缀只增不改——KV cache 纪律在新增
功能时依然生效）。壳侧：生成期间输入进队列、提示"下一轮生效"；生成结束
队列余量转下一轮提问（用户的话不能静默蒸发）。

真机验收（全书最有演示效果的一条）：

```
你> 查一下北京天气
（趁生成输入）改成查上海天气
↪ 已接收（队列 1 条），将在下一轮生效
⚙ get_weather {"city":"北京"}
↪ 注入用户中途指令：改成查上海天气
⚙ get_weather {"city":"上海"}        ← 模型真的改向了
```

> **引经据典**｜pi `packages/agent/src/agent-loop.ts`
> pi 把 steer/followUp 做成双队列原语，注释原话："user may have typed while
> waiting / inject before next assistant response"——与我们的语义逐字一致；
> 它还支持 `prepareNextTurn` 每轮换模型/温度。**打断是 loop 的语义，
> 不是 UI 的 hack**——这是它最重要的设计论点，我们照单全收。

## 7.4 v0.10 硬取消：Ctrl-C 不再杀进程

steering 是"下一轮生效"，取消是"现在就停"。通道是 Web 标准 AbortSignal
三层贯穿：

```ts
// 0. 前置：ChatRequest 加 signal?: AbortSignal（内部字段，构造请求体前剥离
//    ——从不进 HTTP 报文；缺省不携带，请求体与旧版同形）
// 1. fetch 层：
const res = await fetch(url, { ...init, signal: req.signal });

// 2. 工具层：外层 signal 与超时 signal 组合——单独听超时会覆盖外层，
//    取消永远传不进工具（AbortSignal.any 组合）
const signals = [controller.signal, ...(outer?.signal ? [outer.signal] : [])];
const ctx = { ...outer, signal: AbortSignal.any(signals) };

// 3. 循环层：流中断 → interrupted 事件；轮首检查（取消后零新请求）
```

第 4 章②讲过 abort 的协作式本质——这里补齐它的另一半：**取消的边界**。
abort 后：fetch 立刻抛 AbortError；正在执行的工具在下个"听牌点"醒来退出；
但**已经发生的副作用不回滚**（工具若已写了文件，取消不会删它）。取消语义
是"停止后续"，不是"时间倒流"——工程上把它如实写进文档比假装能回滚诚实。

## 深入一层 ③：为什么半截内容绝不回填

流中断时刻，循环里攒着半截 `textBuf` 和半截 `slots`。为什么不组装成
assistant 消息入档（"模型说过的话不该丢吗"）？

1. **半截 tool_calls 是下次请求的污染源**：残缺 arguments 入 messages，
   下一轮模板渲染它、引擎**重新解析历史里的 tool_call args**——非法 JSON
   直接 HTTP 500（真机实录：`Failed to parse tool call arguments as JSON`）。
   这是第 3 章墙 1 在"历史消息"维度的复发
2. **半截正文入档危害小但无益**：对话连续性靠 user 消息与工具结果撑着，
   半句话省下的 token 买不回协议风险
3. **证据不丢**：截获量记进 interrupted 事件（partialText/partialToolCalls）
   ——transcript 里"它说到哪"永远可查，只是不进 messages

原则一句话：**messages 收录"完成的事实"，事件流收录"发生过的一切"**——
两个账本各司其职（第 0 章两条底线的第一次深度应用）。

壳侧 Ctrl-C 语义：第一次取消当前生成回提示符（会话可续——已完成的轮次
和工具结果都在）；1 秒内连按两次退进程。

> **引经据典**｜pi `packages/agent/src/agent-loop.ts`（截断防护）
> pi 对应机制：stopReason==="length" 时把流式抢救出的不完整工具调用**判错**，
> 错误文案指示模型 "Re-issue the tool call with complete arguments"——
> 框架不猜、模型重发。与守卫的截断对策同一契约。

## 7.5 动手与搞坏

- **思考烧穿复现**：请求体手工 `enable_thinking: true` + `max_tokens: 400`，
  问推理题——观察整段只有 reasoning、finish_reason=length（7.1② 亲手复现）
- **steering 假注入识别**：注入点故意改成 round≥1，管道连发两行——第二行
  在首个请求前入队，这不是"中途打断"。验收必须区分两种时序
- **取消后续问**：长任务 Ctrl-C，再问"刚才北京多少度"——会话可续、已完成轮
  的工具结果还在（取消不回滚）
- **半截回填复现（选做）**：把 interrupted 分支改成照常组装入档，触发一次
  取消后继续对话——亲手看 llama.cpp 的 args 500
