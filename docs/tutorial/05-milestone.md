# 第 5 章 第一册总验收：六场景、故障注入与存证制度

> 不写新代码。本章把 v0.1~v0.7 攒下的东西放进一次正式验收：六个固定场景、
> 三组故障注入、一套从头到尾的存证流。**做完本章，你有权说"我搓出了一个
> 能干活且打不死的 agent"——并且有证据**。预计半天。

---

## 5.1 验收的三个层次

到此为止你验过很多东西，但方式是"跑一遍、看一眼"。正式验收要有三层次：

1. **场景**：固定输入 × 期望行为（不只期望输出——"不调工具"也是行为）
2. **故障**：注入失败，验证兜底的行为链（不是验证"没崩"）
3. **证据**：每个场景一份完整存档（请求/响应/过程事件），事后可复核

第三层是本教程与"跟着做就能跑"类教程的分水岭：**没有存证的验收，
两周后你自己都不信**。

> **引经据典**｜clowder-ai `docs/architecture/`（A2A 协议）
> 多 agent 平台 clowder 把验收推到极致：任务"完成"不由 LLM 说、也不由进程
> 退出码说，而由**类型化证据**裁决（PR 的 canonical OID、持久化 revision）。
> 原话："carrier 退出码 0、响应文本，都只是 carrier 事实，不裁决 action 成功"。
> 我们第一册用"场景+存证"起步；第二册 v0.12 用谓词做到机器裁决——
> 那是这条路的终点形态。

## 5.2 场景集：六问

固定六问（每问独立会话，temperature 0）：

| # | 场景 | 输入 | 期望行为 | 验什么 |
|---|---|---|---|---|
| 1 | 单工具 | 查一下北京天气 | 调 get_weather(city=北京)，回答含 28 | 基本链路 |
| 2 | 参数理解 | 那上海呢？ | city="上海"（不是"上海呢"） | 参数语义 |
| 3 | **不滥用工具** | 你好，介绍一下你自己 | **不调工具**，直接回答 | 克制 |
| 4 | 多步编排 | 北京和上海哪边热？差几度？ | 两次调用，比较后回答 | 决策链 |
| 5 | **失败诚实** | 火星天气如何？ | 调用→失败→如实说查不了，**不编造** | 失败语义 |
| 6 | 状态导出 | /dump | 打印完整 messages | 配对完整（肉眼版） |

场景 3 和 5 是含金量最高的两问。**知道什么时候不用工具、失败时诚实**，
比会调工具难得多——4B 在场景 5 上偶尔会"过度自信"编一段火星气象，
每轮验收都要专门盯。

先给工具补上诚实的失败语义（第 3 章火星实验欠的修正）：

```ts
// weather.ts 的 execute 改为：
execute: async (args) => {
  const hit = DB[args.city];
  if (!hit) {
    // 失败也是数据：说清"没有"和"有什么"——给模型的纠错材料
    return { error: `无 ${args.city} 的数据（支持：${Object.keys(DB).join("/")}）` };
  }
  return { city: args.city, ...hit };
},
```

注意这个返回**没有 ok 字段**（信封的 data 里内容自定），模型读到
`{"error":"无 火星 的数据（支持：…）}` 后，正确的下一轮行为就是如实转告。

## 5.4 故障验收：三条行为链

第 4 章跑过三个注入，现在按"行为链"重新验收（不是看结果，是看**链条上每环
都对**）：

| 注入 | 完整期望链 | 哪一环断了算失败 |
|---|---|---|
| `flaky:2` | 调用→瞬时失败×2（用户无感）→重试→成功→正确回答 | 重试次数≠2 或用户看到中间失败 |
| `down` | 调用→耗尽（错误含"不建议再次调用"）→模型**转向如实告知**→不再调用 | 模型无脑再调第三次 |
| `hang`（3s 超时） | 调用→3 秒超时→瞬时判定→按重试策略走→最终用户拿到解释 | 卡死或用户永远等 |

第二行最微妙——它验收的是**错误文案对模型行为的影响**，即 4.2 的
"错误消息就是提示词"是否真的兑现。链断了，回去查文案。

## 5.5 存证制度总装（第一册版）

至此你的存证有三样东西，各司其职：

| 材料 | 内容 | 回答什么问题 |
|---|---|---|
| `request.json` / `response.json` | 当轮协议原文 | 模型看到了什么、吐了什么 |
| `stdout.txt` | 过程输出（事件流的渲染） | 中间发生了什么（⚙/↳/回答） |
| 引擎日志（终端或重定向文件） | timings/cache_n/耗时 | 性能与缓存真相 |

三样对得上，才算"有据可查"——**第二册 v0.12 会把它自动化**（wire 层 tee +
transcript 事件落盘 + 谓词重放），但手做的这一遍不可跳过：自动化的东西你也得
会手动核对，否则它在骗你你不知道。

## 深入一层：跨层证据链——用场景 4 演练一次

拿"北京和上海哪边热"的一次完整存证，把三层证据摆在一起互相印证：

| 层 | 材料 | 应看到 |
|---|---|---|
| 引擎层 | 日志两次请求的计时行 | 第 1 次请求：prompt 全价（cache_n≈0）；第 2 次：cache_n 覆盖第 1 轮全部前缀（含工具结果回填） |
| 协议层 | 两次 response 存档 | 第 1 次响应含 tool_calls(北京)；第 2 次请求的 messages 里有三段（user/assistant+tool_calls/tool 结果）再添新调用 |
| 应用层 | stdout | 两个 ⚙ 与两条 ↳，顺序与协议层一致（源序）；终答含"3 度"（跨轮计算） |

任何一层与其他层矛盾（比如 stdout 有两个 ⚙ 但协议层只有一次 tool_calls 帧），
**以协议层为准、以引擎日志为背景**回溯——这就是"messages 是唯一事实来源"
在验证场景的应用。第二册的 trace 溯源（seq→frame→line→byte）就是把这套
手工对照自动化到字节级。
