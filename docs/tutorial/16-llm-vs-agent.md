## 16.1 分界线：一次前向传播的边界

**精确分界**：LLM 做的事全部发生在一次 forward pass（prefill + decode）内部；
Agent 做的事全部发生在两次 forward pass 之间。

```
LLM 做的（forward pass 内部）          Agent 做的（forward pass 之间）
━━━━━━━━━━━━━━━━━━━━━━━━            ━━━━━━━━━━━━━━━━━━━━━━━━━
语言理解与生成                          执行工具（真实副作用）
单次推理（含内置思维链）                  跨调用状态持久化
语义匹配（意图↔工具说明书）              错误恢复（重试/降级/守卫）
格式生成（能力范围内）                   安全审批（六层管线）
知识回忆（训练数据内）                    长期记忆（跨会话存储）
                                    并行调度 / 取消 / 超时
                                    循环控制（何时停/何时继续）
                                    结果验证（谓词裁决）
                                    崩溃恢复 / 事务 / 回滚
```

用你构建过的东西验证这条线：

**意图理解是 LLM 的**。第 3 章：模型读到 get_weather 的说明书（经模板渲染
成文本），理解"北京多少度"需要调它——语义匹配在 forward pass 里完成。
你写的循环不"理解"任何东西，它只检查 `finish_reason === "tool_calls"`。

**执行是 Agent 的**。`registry.execute()` 调用你的 JS 函数——模型无法执行
任何东西。它生成的 `{"city":"北京"}` 只是一段**文本**；是你的代码把这段
文本变成了函数调用。

**格式纪律的分工最清晰**。第 8 章实测：4B 在纯文本协议下 75% 成功率
（格式失败是 LLM 的能力缺陷）；GBNF 受限解码把它救回 100%（格式保证是
Agent 基础设施的职责）。**同一个问题可以在两侧各解一半**——分界线不是
"谁的能力"，而是"谁的工程能兜住谁的能力"。

**一句话**：LLM 决定"做什么"（生成表达意图的文本），Agent 决定"真的去做"
（执行、持久、恢复、审批、验证）。

## 16.2 单次 Q&A 的 LLM，"agent 能力"到底是什么

LLM 本质是 `text_in → text_out` 的纯函数：没有状态、没有行动能力、
不记得上一轮说过什么（你重发的 messages 才是它的"记忆"）。那为什么
大家说"这个模型 agent 能力强"？

**答案：模型被专门训练过"生成正确的行动表达文本"。**

```
训练前的 LLM：给你描述，续写一段看起来合理的回答
训练后的 agentic LLM：给你描述 + 工具说明书，它能生成——
  ① 正确的 tool_call 格式        （语法层面）
  ② 正确的工具选择                （语义层面）
  ③ 正确的参数构造                （知识层面）
  ④ 合理的多步规划                （每步基于真实结果决定下一步）
  ⑤ 从错误消息中恢复              （读到"参数校验失败"能自纠）
```

这五件事**全部是文本生成**——但它们是"专门面向 agent 循环的文本生成"。
模型在训练时见过海量的（指令+说明书→正确调用→真实结果→下一步）轨迹
数据，学会了在循环的每个决策点吐出正确的下一步。

用你的 v0.14 验证：模型面对"用 execute_code 查两地天气"，写了一段 JS
批量调工具——**这段代码是模型在单次生成里写出来的**。"写代码"的能力在
LLM 里；但"执行代码"（vm 沙箱、CellAuthority、工具回调）在 Agent 里。

所以准确的说法：**"模型的 agent 能力" = 模型生成"行动指令文本"的质量**。
质量越高，循环跑得越顺、越不需要工程兜底——**但循环本身永远在模型外面**。

这也解释了为什么同一个模型在不同 agent 框架里表现天差地别：模型的
"agent 能力"是潜力，框架是把它兑现的机器。差的框架把强模型的潜力
浪费在格式纠错上；好的框架让弱模型的潜力也能兑现（第 8 章：受限解码
+ 4B = 100%，超过裸文本协议 + 9B）。

## 16.3 吞噬趋势：哪些 Agent 工程正在消失

过去三年（2023-2026），这些曾经的 Agent 工程已被模型能力吸收：

| 以前的 Agent 工程 | 被什么吸收 | tagent 对应章 |
|---|---|---|
| prompt 工程让模型输出 JSON | native function calling（格式内置） | 第 3 章 tools 字段 |
| 解析失败重试 | 格式遵从度大提升（失败率骤降） | 第 4 章信封仍在但触发率降 |
| 显式思维链脚手架 | reasoning models（内置推理） | 第 7 章思考开关 |
| 短上下文频繁外部记忆 | 128K~1M 窗口覆盖大多数会话 | 第 6 章裁剪阈值变高 |
| 严格输出模板 | 指令遵从度大幅提升 | 第 8 章受限解码使用率降低 |
| 逐步工具调用的编排 | 模型多步规划能力增强 | 循环轮数减少 |

**规律**：被吞噬的全部是"跟模型搏斗"的部分——格式、解析、重试、模板。
模型变强一层，这些摩擦就薄一层。tagent 的守卫数据佐证：4B 发呆 0/10、
复读 1/6——换更新的模型，这些数字还会更低。

## 16.4 不可吞噬的部分：八件物理上在模型外面的事

但以下八件事**在结构上不可能被模型吸收**——不是"暂时做不到"，
是"概念上就不在模型的定义域内"：

### ① 执行副作用
模型生成 `rm file` 的文本 ≠ 删除了文件。模型是纯函数，没有手。
你的 v0.15 的 shell 工具、write_file——模型永远只能"请求"执行，
执行者是 Agent 代码。

### ② 跨调用状态
模型 stateless，每次调用独立。你的对话历史是**你**在每次请求时重发的
（第 2 章"记忆=重发"）；SessionTree 的分支、MemoryStore 的事实——
它们在 Agent 的存储里，模型只是每次"租用"一下上下文窗口。

### ③ 上下文有限
即使 1M token 窗口，仍有尽头；且注意力稀释随长度加剧（lost in the
middle，第 6 章深入①）。"上下文装得下"≠"注意力用得好"。压缩/投影/
外部检索永远是 Agent 侧的结构。

### ④ 安全审批
谁批准 `rm -rf /`？**模型不能审批自己**——审批者必须在被审批者之外。
你的六层流水线（归一化/hardline/deny/allowlist/确认/白名单）每一层的
存在理由都是"模型不可信任自己对自己的判断"。

### ⑤ 结果验证
模型能生成"验证通过"的文本，但不能**真的**验证。验证需要对照现实：
退出码、文件是否存在、PR 是否 merge。第 15 章的谓词裁决——
`toolCalled` + `toolResultOk` 检查的是**事件流事实**，不是模型说的话。

### ⑥ 循环控制
何时停止、何时重试、何时升级给人——这是**策略**，不是生成。maxIterations
预算、触顶降级、steering 打断、硬取消：全部是 Agent 对循环的治理。
模型可以建议"我完成了"，但 stop 的决定权在 Agent。

### ⑦ 崩溃恢复
模型不会崩溃也不会恢复——它没有进程。effect sandwich 的"意图已持久化
而结算缺席"窗口、幂等终态、SessionTree 的分支恢复——这些是 Agent 的
生命力，与模型无关。

### ⑧ 并发与超时
物理世界的约束。Promise.race 的超时判定、互斥键的 FIFO 串行、
AbortSignal 的协作取消——token 序列里没有"时间"这个维度。

## 16.5 未来图景：分工的深化，不是消灭

综合趋势，Agent 工程师的工作正在**从一侧移到另一侧**：

```
2023 的 Agent 工程                2026+ 的 Agent 工程
━━━━━━━━━━━━━━━━━                ━━━━━━━━━━━━━━━━━━
格式纠错（让模型听话）              安全治理（让模型敢用）
解析重试                           编排设计（多 agent / 工作流）
短上下文管理                        验证与审计（谓词 / lineage）
prompt 调优                        崩溃恢复与持久化
                                  人机边界（自主性分级）
                                  成本与缓存经济学
```

**模型吞噬的是摩擦，不是基础设施。** 就像数据库吞噬了文件管理的"摩擦"
（索引/B树/事务），但没有消灭对数据库工程师的需求——需求反而更专业了。

对你（读者）的启示：

1. **不要押注"模型永远弱"**——跟模型搏斗的工程会贬值。你的格式纠错、
   解析重试，三年后可能不需要了
2. **要投资"模型永远碰不到"的**——安全、验证、状态、编排、恢复。
   这些不但不贬值，随着模型变强（能干的事更多更危险），反而更值钱
3. **理解循环的人永远稀缺**——模型再强，总得有人知道循环在哪里、
   状态在哪里、边界在哪里。因为模型自己不知道这些，也不需要知道
