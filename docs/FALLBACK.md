# Agent 兜底工程模式（HARNESS FALLBACK PATTERNS）

> 版本：v1.0 ｜ 日期：2026-08-31
> 来源：Step 1~5 逐步「故意搞坏」实验的实战沉淀——每一条都有失败实例与存证。
> 核心命题：**agent 的可靠性不取决于模型多强，而取决于壳（harness）替模型兜住多少底。**
> 关联：[ARCHITECTURE.md](ARCHITECTURE.md)（结构）｜ [REQUIREMENTS.md](REQUIREMENTS.md)（各 FR）｜ 实例存证见 captures/

## 0. 总纲：把纪律从模型身上挪到工程上

弱模型（4B 级）的不可靠是**原理性的**：格式自律差、会幻觉、会复读、思考不收敛。
兜底工程的基本手法是把每一类失败模式对应到一层**系统级机制**，让模型「想错也错不成」：

| 模型失败模式（实测实例） | 兜底机制 | 实现位置 |
|---|---|---|
| 输出不合格式 / 写错工具名 | **受限解码**：response_format json_schema，工具名 enum 锁死 | client.ts responseFormat（FR-31） |
| 没等工具结果就编数据（幻觉 25°C） | 行动协议 + Observation 回填：数据只能来自系统追加 | react.ts 循环（FR-26） |
| 工具失败就崩 / 卡死 | 恒不抛契约：一切失败转错误信封回填；超时兜底 | tools.ts 四段校验 + 执行策略（FR-12/13） |
| 同样的错一再重犯 | 确定性失败不重试；瞬时失败重试有上限，耗尽信封带「不建议再调」 | 错误分类表（FR-13/14） |
| 无限循环调工具 | 迭代上限 + **降级终答**（协议级禁工具，不靠 prompt 恳求） | loop.ts degradeOnCap（FR-15） |
| 上下文无限增长 | 双水位裁剪：回合完整（不拆 tool 配对）+ 前缀稳定（cache 友好） | memory.ts（FR-19/20） |
| prompt 层开关失效（/no_think） | 开关落在协议层（chat_template_kwargs）而非消息文本 | Step 4 考据（FR-23） |

## 1. 各模式详解

### 1.1 受限解码：格式纪律的最后防线

**实例（Step 5，captures/step5-react/）**：4B + 关思考跑文本协议 ReAct，三种死法——
① 零样本：完全无视格式直接幻觉作答（编造 25°C，真实 mock 是 28）；
② few-shot 后：陷入审议复读（连说五遍"我需要调用工具"却不输出 Action）；
③ 写错工具名（`weather`）+ 加戏参数（`lang`）。
加 few-shot、纠错 Observation 回填都救不动——**格式纪律是解码问题，不是提示问题**。

**兜底**：每轮请求携带 `response_format: json_schema`（llama.cpp 走 GBNF 约束）：
工具名 enum 从 registry 动态生成（工具集变化 schema 自动跟随），模型**物理上**只能输出
`{"thought","action":{"tool"|"final"}}`。同模型同温度，一次输出即合规。

**边界**：约束的是形状不是内容——参数值仍可能错（靠 zod 校验兜底）；思考内容不参与约束。

### 1.2 错误信封：永不吞错，永不崩溃

**实例（Step 1 AC-5，Step 2 AC2-3）**：工具失败、参数非法、未知工具，全部转成
`{"ok":false,"error":...,"issues":[...]}` 回填给模型——错误变成模型可推理的信息，
模型向用户如实说明或换参数（双层 ok：执行链 true + 业务 false，见 weather.test 注释）。

**兜底**：ToolRegistry 恒不抛契约（四段校验：工具名→JSON→schema→执行）。
**边界**：回填给弱模型后它可能不读——所以信封文案要说人话（错误 + 可用列表 + 建议）。

### 1.3 错误分类重试：确定性失败重试无意义

**实例（Step 2 policy.test）**：schema 校验失败重试 3 次必得同果（确定性）；瞬时抖动
（TransientToolError / 超时）重试 1 次即可自愈，**省下模型自己重调的一整轮 LLM**（AC2-2）。
耗尽后的信封携带 `retriesUsed` + 「不建议再次调用」——给模型的降级指令。

### 1.4 触顶降级：协议保证优于 prompt 恳求

**实例（Step 2 AC2-4）**：迭代触顶时不报错死掉，而是追加一次**不带 tools 字段**的请求——
模板层没有工具段，`finish_reason` 不可能是 tool_calls，模型"想调也没得调"。
**教训一般化**：凡是「希望模型不做 X」的需求，优先用协议裁剪能力（不传字段、受限解码），
其次才是提示词恳求——后者对弱模型不可靠。

### 1.5 双水位裁剪：遗忘也要讲工程

**实例（Step 3 AC3-3/4）**：上下文超预算一次裁到低水位（回合完整，tool 配对永不拆散），
两次裁剪之间前缀完全稳定——KV cache 持续命中（实测 78%）；「每轮裁一点」每轮付全量
prompt 处理税。**裁剪即遗忘要明示**（事件 + 渲染），messages 仍是唯一事实来源。

### 1.6 开关与约定要落在协议层

**实例（Step 4 考据）**：`/no_think` 消息标记两引擎均失效（Qwen3.5 模板不认）——
建立在模型自觉上的约定是脆弱的。正确开关 = 请求级 `chat_template_kwargs.enable_thinking`
或引擎级 `--reasoning`。**一般化**：agent 的能力开关应尽量映射到协议字段或引擎参数。

**移动端实证（R3，2026-09-01）——防过度思考是 agent 的本职**：同一个「strawberry
里有几个 r」问题，4B 开思考内耗 1251 token / 90 秒（1224 个 reasoning 增量顺带把手机
渲染线程压垮），关思考 131 token / 7.9 秒**且答对**。与 Step 4/8 结论（思考不收敛：
4B 82% → 9B 68%）合成完整证据链：**默认关、按需开、开就给足预算**——开关落在
协议层一行字段，价值 9.5 倍 token。另一面：壳也要防「过度渲染」——逐 token 全量
重排是 O(n²)，增量必须节流批刷（AC9-3）。

## 2. 兜不住的部分（诚实边界）

- **内容质量兜不住**：约束解码保证格式，不保证参数值正确（靠校验）与答案正确（靠模型）
- **弱模型的思考不收敛**（Step 4：1200 token 烧穿，开放任务尤甚）——只有换模型或给足预算
- **非确定性工具**（真实 API）下，任务级复现只保证流程可走通，不保证结果相同
- prompt 恳求并非全无用处（system prompt 的行为规则仍有效），只是**不能作为唯一防线**

## 3. 检查清单（新能力接入时过一遍）

1. 模型输出会破坏格式吗？→ 能受限解码就受限解码
2. 失败路径全部回填了吗？→ 恒不抛契约 + 人话信封
3. 重试分类了吗？→ 确定性失败立即返回，瞬时失败限量重试
4. 循环有上限吗？触顶有降级吗？→ maxIterations + 无工具终答
5. 上下文有预算吗？裁剪保配对吗？→ 双水位 + 回合完整
6. 开关落在协议层了吗？→ 查引擎/协议字段，别信消息文本约定
7. 兜底动作可观测吗？→ 事件进 transcript，存证可回放
8. 验证手段本身验证过吗？→ 构建校验查退出码而非文本匹配（实测教训：grep 模式写错
   连续漏检构建失败，功能静默变死代码）
